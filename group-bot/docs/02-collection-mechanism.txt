ESnow — МЕХАНИЗМ СБОРА И ОБРАБОТКИ ИНФОРМАЦИИ
Дата описания: 25.11.2026.
Основание: текущие bot.py, sources.py, monitoring.py, audit_sources.py и games.json в main репозитория Moseses-Code/esnow-game-updates-bot.
Версия bot.py: 2026.11.14-keyboard. Текст тестовой доставки в текущем monitoring.py: «тест».
Документ описывает существующий код, а не планируемые функции.

1. ОБЩАЯ СХЕМА

games.json → запрос к онлайн-источнику → разбор ответа → строка версии/сигнала →
сравнение с state.sqlite3 → запись изменения в очередь → отправка через Telegram →
фиксация результата и отображение в /last.

ПК администратора выполняет Python-процесс. Он не проверяет локальные установки игр.
Обновления не устанавливаются автоматически. Интернет нужен и для источников, и для Telegram.

2. ФАЙЛЫ И ИХ НАЗНАЧЕНИЕ

games.json — название, внутренний ID, лаунчер, тип источника, AppID или другие параметры.
sources.py — HTTP-запросы и адаптеры преобразования ответов в идентификатор версии.
bot.py — цикл проверок, сравнение версий, очередь и Telegram-команды.
monitoring.py — предупреждения, история и тест доставки.
settings.json — токен Telegram, ID владельца, необязательный ID группы, интервал проверок. Файл содержит секрет: его нельзя публиковать.
state.sqlite3 — последняя версия каждой игры, очередь, история, состояние предупреждений.
bot.log — журнал ошибок; ротация примерно по 2 МБ, до трёх резервных файлов.
audit_sources.py / CHECK-SOURCES.cmd — независимая диагностика источников.
source-check.json — результат этой диагностики. Основной бот не использует его как базу сравнения.
cacert.pem — дополнительные доверенные центры сертификации для HTTPS.

3. ЗАПУСК

Бот читает settings.json и games.json из своей папки.
Из списка исключаются записи enabled=false; при отсутствии enabled запись включена.
Проверяются уникальность внутренних ID и допустимый интервал: не меньше 60 секунд.
По умолчанию интервал равен 300 секундам.
Настройки и список игр не перечитываются автоматически: после изменения файлов нужен перезапуск.
SQLite создаёт недостающие таблицы и мигрирует старую очередь; старые записи без времени остаются без выдуманной даты.
Захват адреса 127.0.0.1:47831 предотвращает одновременный запуск второго экземпляра на том же адресе.
Для автозапуска предусмотрен AUTOSTART.cmd; ручной запуск — RUN.cmd.

4. КОГДА ВЫПОЛНЯЮТСЯ ПРОВЕРКИ

Первый обход начинается сразу после запуска.
Запросы к игровым источникам выполняют четыре рабочих потока. Остальные игры ждут свободного потока.
Основной цикл примерно раз в секунду забирает готовые результаты.
Отправка может начаться до окончания всего обхода: ждать последнюю игру не требуется.
Следующий обход начинается не ранее чем через заданный интервал от начала предыдущего и только после завершения предыдущего.
Если обход занимает больше пяти минут, период фактически увеличивается.
Время ожидания отдельного HTTP-запроса — 25 секунд. Это не жёсткий лимит полного обхода или адаптера: один адаптер может выполнять несколько запросов.
Внешняя задержка источника также влияет на скорость обнаружения.
Фиксированных отчётов в 08:30/20:30 в этой версии нет.

5. ПОЛУЧЕНИЕ И ПРОВЕРКА ОТВЕТА

В зависимости от адаптера используются:
— HTTPS GET с JSON;
— HTTPS GET с HTML и регулярные выражения;
— HTTPS GET с XML или текстовой таблицей;
— HTTPS HEAD с чтением ETag.

HTTPS проверяет сертификаты, дополнительно загружается cacert.pem, если он есть.
Проверка сертификатов не отключена.
Адаптер read_version(game) должен вернуть непустую строку.
Это может быть buildid, номер версии с номером сборки, хеш манифеста, ETag-хеш или ID новости.
Проверки формата зависят от адаптера; универсальной проверки свежести и подтверждения выпуска на всех источниках нет.
Список конкретных адресов и способов разбора дан в первом файле.

При ошибке HTTP, тайм-ауте, неверной структуре или невозможности получить сигнал игра считается непроверенной.
Последняя успешная версия при этом сохраняется: ошибка не превращается в новую версию.
В журнал и диагностику передаётся название класса ошибки, без полного текста исключения с возможными секретами.
Автоматической подстановки версии из другого адаптера при сетевой ошибке в текущем коде нет.
Существующие Steam-сигналы для других лаунчеров — это заранее настроенный источник в games.json, а не аварийная подстановка.

6. СРАВНЕНИЕ ВЕРСИЙ

Для каждой игры SQLite хранит последнюю строку version по внутреннему game ID.

Случай А: записи ещё нет.
Версия сохраняется как исходная. Сообщение не создаётся.
Поэтому обновления, вышедшие до первого успешного наблюдения, автоматически не рассылаются.

Случай Б: строка совпадает с сохранённой.
Изменение не регистрируется. Повторного сообщения нет.

Случай В: строка отличается, ревизия источника не изменилась.
В одной транзакции создаётся запись notices и обновляется последняя версия.
У события записывается время обнаружения на ПК, а не достоверное время выпуска издателем.

Случай Г: изменилась source_revision.
Первое успешное наблюдение создаёт новую базовую версию без уведомления.
Это предотвращает ложную рассылку при переходе, например, с номера новости на номер сборки.
Ревизию должен менять разработчик вместе с несовместимым изменением источника; автоматического сравнения всего кода адаптера нет.
Реальное обновление во время такой смены нельзя отделить от изменения формата.

Сравниваются строки на неравенство, а не только рост номера.
Откат тоже считается изменением. Последовательность A → B → A → B создаёт три события.
Колебание данных нестабильного источника также может создать события: универсального подтверждения двумя наблюдениями нет.
Если источник менялся несколько раз между обходами и вернулся к прежнему значению, такое изменение может остаться незамеченным.

7. ОЧЕРЕДЬ И ДОСТАВКА

notices хранит игру, новую версию, название, время обнаружения, sent, время отправки, последнюю ошибку и ID получателя попытки отправки.
При успешном ответе Telegram запись получает sent=1.
На обычном проходе отправка очереди планируется примерно каждые 2 секунды; после ошибки — через 30 секунд.
Это плановые интервалы, а не гарантия: сетевые запросы и обработка других действий могут задерживать цикл.
Отправляются ожидающие записи по ID, от старых к новым. Ошибка прерывает текущий проход очереди.

Получатель:
— если группа привязана, используется chat_id группы;
— иначе используется owner_chat_id владельца;
— ошибка отправки в группу не переключает доставку на личный чат.

Получатель определяется при попытке отправки. После перепривязки ожидающие события пойдут в текущий настроенный чат.
Текст обычного игрового уведомления — только название, например «Dota 2».
В личных сообщениях владельцу API добавляет актуальную клавиатуру; в группе её нет.
Очередь и отметки отправки переживают перезапуск при сохранении state.sqlite3.

Успешный ответ Telegram означает принятие сообщения сервисом, а не прочтение человеком.
Если Telegram принял сообщение, но ответ потерялся или процесс завершился до записи sent=1, повторная отправка может создать дубль.
Гарантии «ровно один раз» в этой реализации нет.

8. ПРЕДУПРЕЖДЕНИЯ ВЛАДЕЛЬЦУ

Источники: после трёх неудачных проверок подряд создаётся основание для предупреждения.
Успешная проверка сбрасывает счётчик.
Доставка: основание для предупреждения возникает при первой ошибке отправки игрового уведомления.
Предупреждение отправляется только в личный чат владельца, один раз до восстановления.
После ранее доставленного предупреждения отправляется одно сообщение о восстановлении.
Для доставки восстановление подтверждается успешной отправкой игрового уведомления, а не просто ответом /status.

Состояние хранится в incidents и переживает перезапуск.
Проверка диагностических сообщений планируется каждые 10 секунд, после ошибки их отправки — через 60 секунд.
За один проход отправляется не больше пяти диагностических сообщений.
Если источник восстановился до того, как предупреждение удалось доставить, устаревшее предупреждение не отправляется.
При полной недоступности Telegram или интернета немедленное оповещение невозможно.
Сам остановленный бот не может сообщить, что он остановился.
Это предупреждения о мониторинге и доставке, а не DOWN/WORK игровых серверов.

9. КОМАНДЫ И КЛАВИАТУРА

Команды принимаются только в личном чате владельца с проверкой chat ID и sender ID.
Telegram getUpdates опрашивается отдельным рабочим потоком, но ответы на команды обрабатывает основной цикл.
Смещение telegram_offset сохраняется в metadata.

«Статус» /status и /start:
время запуска, последний завершённый обход, успешные/ошибочные ответы,
прогресс текущего обхода, интервал, получатель и очередь.
Статистика текущего процесса после перезапуска собирается заново.
/status не запускает внеочередной обход и сам по себе не доказывает точность источников.

«Последние обновления» /last:
10 последних записей notices с версией, временем обнаружения, состоянием доставки.
У старых записей без времени показывается, что оно не было записано.

«Источники» /sources:
ограничения адаптеров и последние ошибки, известные текущему процессу.

«Проверить доставку» /test:
в настроенный чат отправляется «тест».
Если получатель — группа, владельцу отдельно приходит результат.
Тест не меняет игровые версии и не попадает в историю обновлений.
delivery_tests хранит результат по update_id, чтобы повторная обработка той же команды не отправляла завершённый тест снова.
Для нового теста нужно отправить новую команду.

Старые кнопки проверки обновлений и публикации сводки больше не выполняют прежние действия: они предлагают обновлённую клавиатуру.
В текущем интерфейсе нет команды принудительного внеочередного обхода.

10. НЕЗАВИСИМАЯ ДИАГНОСТИКА

CHECK-SOURCES.cmd запускает audit_sources.py.
Он использует те же адаптеры, четыре рабочих потока и активные записи games.json.
Сохраняет source-check.json: ID, название, лаунчер, источник, классификацию, ограничение,
результат, строку версии либо класс ошибки и время проверки в UTC.
Не читает токен Telegram, не отправляет сообщения, не меняет state.sqlite3 и не сравнивает с историей основного бота.
Повторный запуск перезаписывает source-check.json.

11. ЧТО ЭТА СХЕМА НЕ ГАРАНТИРУЕТ

— Наличие обновления на конкретном установленном компьютере.
— Обнаружение всех обновлений по новостям.
— Полное совпадение релизов между Steam, EA App, Epic и BSG.
— Отсутствие задержки сторонних зеркал и поэтапного выпуска.
— Отсутствие повторной доставки при потере ответа Telegram.
— Определение точного времени выпуска и размера скачивания.
— Оповещение об отказе собственного процесса без внешнего наблюдателя.

Практический смысл сообщения: «Изменился отслеживаемый сигнал этой игры».
Достоверность вывода о клиентском обновлении зависит от источника, описанного в первом файле.
